# Shape a source-first interface around durable Source Guides

Labels: enhancement, completed
Parent: [Chat Session error follow-up](../MAP.md)

## Outcome

Produce a bounded UI PRD and implementation issues that make relevant Source
Articles easy to consult across the whole interaction, from entering a question
to consulting results. Explain why each article matters and allow articles to
be grouped by that relevance. The primary reader is a voter. The tool serves a
librarian's role: its guidance must not substitute for reading the actual articles.
Relevant sections should be highlighted on the actual article page and linked
directly when possible. The voter interface displays no Article Chunks.
Each question has a durable, updateable Source Guide organizing its resources.
A voter can start multiple questions independently, browse their Source Guides,
or edit a question. Question lineage is not a requirement. This supersedes the
earlier temporary-workspace/history decision and immutable-artifact framing.
The interface runs locally in this iteration. Collapsed Search details explain
collections, dates, search completion, and result limits. Q1-Q32 are settled;
the maintainer requested publication through to-spec. The
[Source Guides PRD](../../../projects/source-guides/PRD.md) and
[nine implementation tickets](../../../projects/source-guides/PRD.md#implementation-tickets)
are published. The tickets declare blockers and use `ready-for-agent` labels.
Application implementation has not begun.

These are revisable requirements for this product iteration, not architectural
constraints. The Source Guide presents information through views suited to the
question, including contrasting positions, differing accounts, and timelines.
Future iterations can change these views and interactions without an ADR.

## Triage Notes

**What we've established so far:**

- The maintainer expects presentation and interaction work to require UI changes.
- On 2026-10-07, the maintainer chose the whole interaction as the design scope
  and the voter as the primary reader. Relevant articles may be grouped by what
  matters to the question; each needs guidance explaining why it matters. The
  tool must direct readers to the actual articles rather than supply a standalone
  reporting account.
- Relevance notes identify what an article helps someone investigate, such as
  "Read this for the supporters' arguments about construction wages." They do
  not recount those arguments or conclusions.
- Groups follow the question. For an arguments question, the maintainer's
  example is "the supporters' arguments" and "the detractors' arguments".
  Chronological developments and differing accounts are distinct relationships;
  the earlier annotation does not establish that its articles disagree.
- One Source Article may appear in multiple Article Groups with a relevance
  note specific to each group. Membership does not assign the article a political
  position. Create groups only where retrieved material supports them.
- No Article Chunks appear in the voter interface. Use them internally to locate
  relevant sections, then direct the reader to those sections on the actual
  article page. Link construction, highlighting support, and fallback behavior
  use a verified original-text target when available, with the ordinary article
  URL as fallback. Highlighting is best-effort; a stored-text match does not
  establish that the live page still matches.
- Skip the Query Rewrite in the rebuilt iteration. Coordinate the change with
  the original-question baseline issue. Search directly on submission without
  a second approval step. For an unresolved referent, ask the voter to identify
  it and edit the question. Broad but meaningful questions may proceed. Routing
  details still need a bounded implementation contract.
- Voters may refine a search or ask a related question from the results view.
  Show the complete searchable question before each search, with dates, names,
  and scope visible and editable. Each search has its own results and limits.
- "Edit search" restores the previous complete question for direct editing and
  submission. A new question starts with an empty input. Refinements do not
  automatically generate a model-authored replacement question.
- When useful articles cover only part of the question, show the supported
  groups and briefly identify the part for which this search found no matching
  articles. Search failures receive a distinct disclosure. Neither result proves
  the corresponding articles or arguments do not exist.
- Organize the interface around durable per-question Source Guides rather than a
  message transcript or a temporary workspace. Multiple questions can run
  independently and each Source Guide may be updated. There is no requirement
  to retain lineage between questions. Updating the same question updates its
  existing guide; editing the question creates a separate guide.
- Each article displays a linked title, Publication, publication date, relevance
  note, and a relevant-section link when available. Omit unavailable metadata.
  Show all articles passing the final relevance gate, ordered by relevance unless
  the question requests chronology. Article links open a separate tab and
  preserve the reader's guide.
- Questions and their Source Guides are durable and browsable.
  This replaces the earlier Q16 decision limiting history to an open workspace.
  Save the question at submission, then retain completed, empty, Declined,
  Deferred, failed, and cancelled outcomes after reload or application restart.
  Opening a guide restores it rather than rerunning its search. Updates are
  explicitly requested; opening, new articles, and schedules do not trigger
  automatic updates in this iteration.
- Searches continue independently of browser navigation or closing the page
  while the local application remains running. Multiple guides can have running
  searches; the displayed guide does not own all running work.
- Keep previous content during an update. A failed attempt preserves that
  content, shows failed state, and retains last successful update/retrieved
  information on the guide. Do not label saved content as newly retrieved.
  A successfully completed update replaces the content, including when it
  finds no relevant articles.
- Each running search offers Cancel. Cancellation affects only that search,
  preserves previous guide content, and prevents late results from replacing
  retained content or a newer result.
- When the local service stops mid-search, preserve the guide and mark the
  attempt interrupted after restart. Offer Retry without automatic replay.
- If Article Group organization is unavailable, list the articles. Every article
  should still have a reason identifying which part of the question it supports.
  Group organization and per-article relevance are distinct requirements; do not
  invent a separate grouping pipeline or assume grouping failure means all
  relevance guidance failed.
- Every included article must have a defensible relevance reason. Omit an article
  when no such reason can be supplied: this is the final relevance gate after
  retrieval has organized and bounded the material requiring assessment. Do not
  confuse successful rejection of irrelevant articles with assessment failure.
- Reuse the existing Declined and Deferred concepts for requests the system
  cannot represent. The agent judges retrievability or presents the assessment
  after retrieval. Coordinate with the evidence-support issue rather than add
  a separate UI-owned eligibility policy.
- Display available collections and dates near the input. Collapsed Search
  details show collections, date ranges, search completion or failure, and result
  limits. Technical diagnostics remain separate development information. Neither
  the main voter view nor its details displays Article Chunks.
- This iteration remains local. Public hosting is separate work.
- `render_answer` currently emits every selected stored Article Chunk with its source and
  emits disagreement notes after those passages. Code inspection confirms the
  mechanism behind `chunks-as-output`; it differs from the Source Guide design.
- `RetrievalAnswer` already supplies source citations, relevance notes,
  disagreements, evidence passages, and coverage/failure disclosures.
- Local Retrieval Chat already has loopback security, isolated one-question
  sessions, approval/correction flows, and expandable Search details. Those are
  existing contracts; this design deliberately replaces rewrite approval and
  temporary history while preserving security and search isolation.
- The stock frontend currently receives Markdown answers and Search details
  events. It does not provide this guide interaction. No frontend framework
  has been selected; choose it through the bounded implementation PRD.
- There is no saved application question/result facility. SQLite offers existing
  persistence conventions and typed selected evidence can be serialized, but
  runtime Chat Sessions are process-local and work belongs to an HTTP operation.
  Durable guides and browser-independent execution are new lifecycle contracts.
  Retention-bound Logfire telemetry is not the durable guide store.
- Citations currently provide ID, title, URL, and optional publication date.
  Publication metadata and targeted section links need explicit wiring. Stored
  chunks can contain coreference replacements; original Story text exists but
  reliable original section offsets and DOM anchors are not retained.
- Production startup already runs the shared Jev, sparse, and dense retrieval
  path for eligible questions. Preserve current branch participation from
  [ADR 0023](../../../../docs/adr/0023-jev-constructs-cypher-in-the-shared-chat-retrieval-path.md)
  when removing rewriting rather than inventing a new routing decision.

## Controlled acceptance examples

| Situation | Required behavior |
| --- | --- |
| Supporters/detractors question | Reading directions under supported groups; do not recount their arguments. |
| One article serves both groups | Include it in both with distinct relevance notes. |
| Group organization unavailable | List the relevant articles with their per-article reasons. |
| Article lacks defensible relevance | Omit it at the final relevance gate. |
| Only part of the question has useful sources | Show those sources and identify the unmatched part without claiming absence. |
| Search/relevance assessment succeeds but selects nothing | Search-specific empty result, distinct from failed guidance or Deferred. |
| Retrieval branch fails | Preserve useful completed sibling evidence and disclose failure. |
| Guidance cannot run or validate | Failed assessment, not a successful search with no matches. |
| Original target wording cannot be verified | Ordinary article URL remains available; display no chunks. |
| Question has an unresolved referent | Request identification through direct editing, without rewriting. |
| Several questions run | Each has its own durable guide and independently continuing search. |
| Page closes during a search | Search continues while the local service runs; reopening restores status/content. |
| Existing guide updates successfully | Replace that guide's content and retrieval status. |
| Update fails or is cancelled | Keep previous content and retrieval date, show the attempt's outcome. |
| Question is edited | Create a separate guide without changing the original or requiring lineage. |
| Service stops mid-search | Durable guide shows interrupted attempt and Retry; no automatic replay. |
| Agent returns Declined or Deferred | Preserve existing typed eligibility/coverage outcome and explanation. |

## Dependencies and scope

UI shaping can proceed alongside RAG evaluation. Implementation coordinates with
the chosen original-question interaction and coverage disclosure contracts.
Changing retrieval scores, adding another answering agent, and collecting new
annotations are outside this item. Browser verification requires explicit
maintainer authorization under the repo instructions. The maintainer explicitly
authorized browser verification for the implementation during to-spec on
2026-10-08; the PRD records that verification as part of acceptance.

Guide monitoring, public hosting, question lineage, an immutable artifact model,
and guaranteed live-page section alignment are outside this iteration. Prompt
implementation must use new immutable explicit versions under ADR 0022. Reuse
the current retrieval and Chat Agent handoff, and coordinate original-question
and coverage work rather than creating competing implementations.
