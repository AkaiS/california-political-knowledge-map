# Findings: Prompt Iteration in Pydantic Evals and Logfire

Not tied to a numbered issue. Sources are the versions of `pydantic-evals` and `logfire` installed in this worktree's venv, read directly, plus Pydantic's own first-party documentation; where a claim rests on inference rather than on read code or a documented sentence, it says so. Installed at the time of writing: `logfire` 4.37.0, `logfire-api` 4.37.0, `pydantic-evals` 2.0.0, `pydantic-ai` / `pydantic-ai-slim` 2.0.0, `pydantic` 2.13.4.

## There is no prompt API; there is a managed-variable API

The Logfire Python SDK has no `prompt` module, no `Prompt` class, and no `get_prompt()` function. Grepping the installed package for `prompt` finds only unrelated CLI confirmation text and one comment about template escaping (`.venv/lib/python3.13/site-packages/logfire/variables/abstract.py:222`). Everything Logfire calls "Prompt Management" is a server-side and UI-side layer over the managed-variables machinery: the docs state that every prompt is "backed by a managed variable" named `prompt__<slug_with_underscores>`, so the prompt with slug `welcome-email` is served from the variable `prompt__welcome_email`, and names beginning `prompt__` are reserved ([Prompt Management concepts](https://pydantic.dev/docs/logfire/prompt-management/concepts/)). The MCP server's own tool descriptions say the same thing from the other side: `variable_list` returns prompt-backed variables with `kind='prompt'` and a `prompt_slug`, and directs you to `variable_manage` for "versions, labels, and rollout" while the `prompt_*` tools cover only the template text and playground settings.

The consequence for code is that the runtime API is the variables API. A prompt is fetched with [`logfire.template_var`](https://pydantic.dev/docs/logfire/prompt-management/application/) — `logfire.template_var(name='prompt__<slug>', type=str, default='', inputs_type=InputModel)` — and then `with prompt_var.get(InputModel(...), label='production') as resolved: prompt = resolved.value`. `logfire.var` is the same thing without Handlebars rendering. Both are thin module-level aliases onto the `Logfire` instance (`logfire/__init__.py:103-104`), and their real signatures are `Logfire.var(name, *, type=None, default, description=None) -> Variable[T]` and `Logfire.template_var(name, *, type=None, default, inputs_type, description=None, template_mismatch_policy=None) -> TemplateVariable[T, InputsT]` (`logfire/_internal/main.py:2510` and `:2636`). Names must be valid Python identifiers, and registering the same name twice on one instance raises — the check is unlocked because variables are expected to be declared once at import (`logfire/_internal/main.py:2580-2596`). Using any of this requires the `logfire[variables]` extra; `logfire/variables/__init__.py:98-117` raises a directed `ImportError` on first *use* rather than at import, so a project that never touches variables is unaffected.

`Variable.get(targeting_key=None, attributes=None, *, label=None)` and `TemplateVariable.get(inputs, targeting_key=None, attributes=None, *, label=None)` return a `ResolvedVariable` (`logfire/variables/variable.py:945` and `:1036`). The template pipeline is documented in the source as "resolve → compose `@{refs}@` → render `{{}}` → deserialize" (`logfire/variables/variable.py:970-975`). Passing `label=` bypasses rollout and targeting entirely and selects a named label directly, and "if the label doesn't exist in the configuration, falls back to default resolution" (`logfire/variables/variable.py:955-960`) — a silent fallback, not an error, which matters if you intend a label to pin an experiment.

## Versioning, labels, rollout and targeting are a data model you can read

The client-side shape of the config is fully declared in `logfire/variables/config.py`. A `VariableConfig` carries `labels: dict[str, LabeledValue | LabelRef]`, a default `rollout: Rollout`, an ordered `overrides: list[RolloutOverride]`, `latest_version: LatestVersion | None`, a `json_schema`, optional `aliases`, and `template_inputs_schema` (`logfire/variables/config.py:293-324`). A `LabeledValue` is `{version: int, serialized_value: str}` and a `LabelRef` points at another label or at the reserved targets `latest` / `code_default` (`config.py:200-230`). A `Rollout` is `labels: dict[str, float]` of weights summing to at most 1.0, where "an empty dict means 'use code default'" (`config.py:233-238`). A `RolloutOverride` is a list of conditions plus a rollout, and overrides are "evaluated in order; first match takes precedence" (`config.py:284-308`). The condition vocabulary is `ValueEquals`, `ValueDoesNotEqual`, `ValueIsIn`, `ValueIsNotIn`, `ValueMatchesRegex`, `ValueDoesNotMatchRegex`, `KeyIsPresent`, `KeyIsNotPresent` (`config.py:50-174`), all re-exported from `logfire.variables`.

Versions are immutable and sequential and labels are mutable pointers — the documentation calls labels reassignable "instantly changing what value is served to traffic assigned to that label" ([managed variables](https://pydantic.dev/docs/logfire/manage/managed-variables/), [UI guide](https://pydantic.dev/docs/logfire/manage/managed-variables/ui/)). Weighted selection is deterministic per `targeting_key`: the docs are explicit that "the same user always gets the same label, which is essential for application behavior consistency when A/B testing." When no `targeting_key` is passed at the call site, the SDK falls back to a contextvar set by `logfire.variables.targeting_context`, and then to `f'trace_id:{current_trace_id:032x}'` if a trace is active (`logfire/variables/variable.py:895-903`). That last fallback is worth noticing before running a rollout inside an eval: every case in one experiment shares a trace, so an unkeyed rollout would assign the whole experiment to one bucket rather than splitting it.

Previewing is a server capability, not an SDK one. The MCP tool `prompt_preview` renders a saved prompt without calling a model, expanding `@{...}@` composition against live variable values and filling `{{...}}` from supplied `inputs`, with an explicit note that "Model execution (`prompt_run`) stays off the MCP surface." `variable_resolve` answers the complementary question — what a client would receive right now and why — returning `reason` as one of `STATIC / TARGETING_MATCH / SPLIT / DEFAULT` alongside `label` and `version`. Those server-side reason strings are a different vocabulary from the SDK's `ResolutionReason` literal (`resolved`, `context_override`, `missing_config`, `unrecognized_variable`, `validation_error`, `other_error`, `no_provider`, `code_default` — `logfire/variables/abstract.py:53-73`); do not assume they map one-to-one.

## Fetch, cache and failure

Remote resolution never hits the network on the resolution path. `LogfireRemoteVariableProvider` holds a whole `VariablesConfig` in memory and refreshes it from `GET /v1/variables/` on a background daemon thread on a polling interval, with an SSE listener that can force an early refresh (`logfire/variables/remote.py:289-360`). `get_serialized_value` reads the cached config; it only blocks on a fetch when no fetch has yet been attempted *and* `block_before_first_resolve` is set (`remote.py:361-388`).

Failure is swallowed by design. `refresh()` wraps the request in a bare `except Exception` covering "ConnectionError, Timeout, UnexpectedResponse, JSONDecodeError, etc. to prevent crashing the user's application on failures", logs the error, sets `_has_attempted_fetch = True` so subsequent calls do not block against an unreachable server, and returns (`remote.py:337-352`). A `ValidationError` while parsing the config is logged and leaves the previous config in place (`remote.py:354-360`). If no config was ever obtained, `get_serialized_value` returns `ResolvedVariable(value=None, reason='missing_config')` (`remote.py:385-386`), and the variable falls back to the in-code `default`. The documentation states the same contract: "if the remote configuration is unreachable due to a networking issue… the SDK returns the code default instead of raising an error" ([managed variables](https://pydantic.dev/docs/logfire/manage/managed-variables/)). Offline, therefore, a prompt silently becomes whatever string is hard-coded as `default=` — with `reason='code_default'` and `version=None` as the only signal. For an evaluation run that is a correctness hazard: a report attributed to "prompt v7" can be a report of the code default unless the run reads `resolved.reason` and `resolved.version` and refuses to proceed.

## What a resolution puts into telemetry

Two mechanisms, and they differ in reach.

First, `Variable._get_result_and_record_span` opens a span named `Resolve variable {name}` (scope suffix `variables`) and sets `name`, `value`, `label`, `version`, `reason`, and, when composition occurred, a JSON `composed_from` (`logfire/variables/variable.py:886-940`). The value is dumped through the type adapter, so the whole prompt text lands on that span. This span can be disabled through the config's variables options (`variable.py:912`).

Second, `ResolvedVariable` is a context manager, and entering it calls `logfire.set_baggage` with `logfire.variables.<name> = <label or '<code_default>'>` and, only when a version actually resolved, `logfire.variables.<name>.version = <version>` (`logfire/variables/abstract.py:134-152`). Logfire registers `DirectBaggageAttributesSpanProcessor` by default (`logfire/_internal/config.py:1122`), and its `on_start` copies every string baggage entry onto each span started inside the block, renaming a colliding key to `baggage_conflict.<key>` (`logfire/_internal/baggage.py:87-109`). So the version identifier propagates *downward* onto spans opened inside `with prompt_var.get(...) as resolved:` — and only downward. A span already open when resolution happens does not receive it. That is exactly the situation of a `pydantic-evals` experiment span, which is opened before the first case runs.

## The shape of a pydantic-evals experiment

`Dataset(name=..., cases=[Case(...)], evaluators=..., report_evaluators=...)` is run by `Dataset.evaluate(task, *, name, max_concurrency, progress, retry_task, retry_evaluators, task_name, metadata, repeat, lifecycle)`, with `evaluate_sync` as the blocking wrapper over the same arguments (`pydantic_evals/dataset.py:281` and `:411`). Nothing in the framework knows about prompts: the task is a single `Callable[[InputsT], OutputT]`, and a grep of `dataset.py` and `reporting/__init__.py` for `prompt` or `variant` returns nothing. A prompt sweep is therefore something you build — one `evaluate` call per variant, with the variant identity carried in `name=` and `metadata=`, or a closure over the prompt bound before the call.

`metadata: dict[str, Any] | None` is the designated hook and is documented only as "Optional dict of experiment metadata" (`dataset.py:291,312`). It travels two ways. It is attached to the returned report as `EvaluationReport.experiment_metadata` (`dataset.py:392-394`, `reporting/__init__.py:320`), and it is written onto the experiment span, nested: `_set_experiment_span_attributes` builds `{'n_cases': …, 'repeat': …, 'metadata': <your dict>, 'averages': …}` and sets it as the single attribute `logfire.experiment.metadata` (`dataset.py:1032-1048`). The span itself is `evaluate {name}` and carries `name`, `task_name`, `dataset_name`, `n_cases`, `gen_ai.operation.name='experiment'`, and a top-level `assertion_pass_rate` when assertions exist (`dataset.py:333-346`, `:1046-1047`). Each case is a child span `case: {case_name}` carrying `inputs`, `metadata`, `expected_output`, and after the run `output`, `task_duration`, `metrics`, `attributes`, `assertions`, `scores`, `labels` (`dataset.py:1101-1152`). The report records `trace_id` and `span_id` of the experiment span (`dataset.py:369-375`), which is what makes a report addressable in the UI.

Report comparison in code is genuinely first-class. `EvaluationReport.render`, `.print` and `.console_table` all take `baseline: EvaluationReport | None`; when a baseline is given, `console_table` returns `renderer.build_diff_table(self, baseline, …)` instead of the flat table (`reporting/__init__.py:373`, `:432`, `:514-566`). `_metadata_panel` diffs the two reports' `experiment_metadata` key by key, styling added keys green, removed red, and changed `old → new` yellow (`reporting/__init__.py:598-620`), and case rows are matched by case name and diffed field by field (`reporting/__init__.py:1076-1103`). Two `EvaluationReport` objects in one process, or two deserialized from files, can be compared without any Logfire involvement — but the framework provides no persistence: there is no `EvaluationReport.load`, and this repo already had to write its own JSON serialization for that reason.

`repeat: int` re-runs each case and groups results by the original case name via `logfire.experiment.source_case_name` (`dataset.py:1117`), which is the framework's answer to run-to-run variance — useful when the difference between two prompt versions is small enough to be noise.

## The join, and what it does not do

`logfire.url_from_eval(report)` turns a report into `{project_url}/evals/compare?experiment={trace_id}-{span_id}` (`logfire/_internal/main.py:919-934`), returning `None` when the project URL or ids are missing. The UI side documents a real comparison workflow: an experiment's "Compare runs" action makes the current run the candidate and lets you choose a baseline "from another run of the same dataset", with an Overview tab of side-by-side aggregates and a Cases tab with a primary metric, a better-score direction, and grouping by outcome ([review experiments](https://pydantic.dev/docs/logfire/evaluate/review-experiments/), [datasets and experiments](https://pydantic.dev/docs/logfire/evaluate/datasets-and-experiments/)). So "compare experiment A vs B" does exist, both in the UI and as `EvaluationReport.print(baseline=...)` in code.

What does not exist is any awareness of a prompt version as a dimension of that comparison. Nothing in `pydantic-evals` reads a managed variable; nothing in `logfire.variables` writes into an eval report; the managed-variables UI guide has no eval integration, and the prompt-management docs describe their own in-UI testing surface — "scenarios are saved test cases", optionally swept over a dataset — which is a separate object graph from `pydantic-evals` datasets and experiments ([prompt management](https://pydantic.dev/docs/logfire/prompt-management/), [scenarios](https://pydantic.dev/docs/logfire/prompt-management/scenarios/)). Grouping experiments by prompt version is something to build.

The build is small, and there are two halves. To make the *report* carry prompt identity, read `resolved.label`, `resolved.version` and `resolved.reason` at resolution time and pass them into `Dataset.evaluate(..., metadata={'prompt': name, 'prompt_version': version, 'prompt_label': label, 'prompt_reason': reason})`; that dict then lands on `EvaluationReport.experiment_metadata`, appears in the metadata panel of a baseline diff, and — because it is the same dict — cannot disagree with what the span says. To make the *trace* queryable, nothing further is needed: the same metadata is already on `logfire.experiment.metadata`. In Logfire's DataFusion SQL (Postgres-like; JSON via `->` and `->>`, per `query_schema_reference`) the experiment rows are `records` where `attributes->>'gen_ai.operation.name' = 'experiment'`, and a per-version comparison is a group-by on `attributes->'logfire.experiment.metadata'->'metadata'->>'prompt_version'` against `(attributes->>'assertion_pass_rate')::float`. Relying on the baggage attributes instead (`logfire.variables.<name>.version`) works only for spans opened inside the resolution block, which as established excludes the experiment span — so the baggage route answers "which prompt version served this model call" and the metadata route answers "which prompt version this experiment tested". They are different questions and the second is the one a report needs.

Two caveats on that plan, both read from source rather than documented. The version is `None` whenever the value came from the code default (`abstract.py:119-122,145-150`), so an offline or misconfigured run produces a report labeled with a null version rather than an error — the run has to assert on `reason` itself. And `get(label=...)` falling back silently when the label is absent (`variable.py:955-960`) means pinning by label is not a guarantee; pinning by reading back `resolved.version` is.

## Where this repo stands

The repo's evaluation subsystem already does the hard half of this. `run_gold_set` passes `experiment_metadata` straight through to `Dataset.evaluate_sync(metadata=...)` with the stated intent that it "reaches the trace and the report by the same route, so the two agree by construction" (`src/knowledge_map/evaluation/engine.py:86-111`), and `write_report` serializes the report alongside `commit`, `dirty`, the structured `deployment`, `gold_set`, `split`, `ran_at`, and a `trace_url` built from the report's `trace_id` (`src/knowledge_map/evaluation/report_file.py:62-97`). `CONTEXT.md:280` defines an Evaluation Run as "one execution of a Gold Set against one task and one Model Deployment" and states that "comparing two runs is a diff of two report files".

What that record does not contain is a prompt identity. The keys in `evals/reports/extraction/20260903T231923Z-25e803d-local-gemma4-26b-1499ceec2201.json` are `task`, `trace_url`, `model`, `deployment`, `commit`, `dirty`, `gold_set`, `split`, `ran_at`, `report`, and the nested `experiment_metadata` repeats `commit`, `deployment`, `gold_set`, `split`, `task`. Prompts here are files — `src/knowledge_map/resources/extraction_prompt.txt`, loaded by `src/knowledge_map/adapters/extraction.py:25`, and the module-level instruction constants in `adapters/coreference.py` and `adapters/policy_areas.py` — so the commit is the only thing standing in for prompt identity. It stands in badly: the commit moves for every change in the repository, so two reports at different commits cannot be told apart as "same prompt, different scorer" versus "different prompt", and `dirty: true` means the commit does not identify the prompt text at all. A content hash of the resolved instruction text in `experiment_metadata` would close that gap without adopting managed variables; adopting managed variables would close it with a server-side version number and the rollout machinery attached, at the cost of the offline failure mode described above and a new hard dependency of an eval run on network reachability — which sits awkwardly against `ALLOW_UNTRACED` and the local-first posture in `src/knowledge_map/utils/telemetry.py`.

## Capabilities that do not exist

Stated plainly, because these were checked rather than assumed: there is no `logfire.get_prompt()` or prompt class in the Python SDK; there is no pydantic-evals concept of a prompt, a variant, or a sweep; there is no automatic link from a resolved prompt version to an `EvaluationReport`; there is no first-class "compare prompt v1 vs v2 across experiments" view (the UI compares two *runs of a dataset*, and any prompt-version dimension has to be smuggled in through experiment metadata); `EvaluationReport` has no load/deserialize counterpart, so cross-run comparison over time requires your own file format; and the prompt-management UI's scenarios/datasets are a separate testing surface from pydantic-evals rather than a view onto it. On stability: neither `pydantic_evals.dataset` nor `pydantic_evals.reporting` carries a beta or subject-to-change notice in the installed 2.0.0 source, but the online-evaluation sink protocol does — batching behavior "may change" and "new fields may be added in future releases" (`pydantic_evals/_online.py:93-104`) — so treat `pydantic_evals.online` as the unstable corner.
