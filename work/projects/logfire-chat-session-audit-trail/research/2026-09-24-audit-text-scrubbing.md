# Audit text scrubbing after PR #25 review

Research date: 2026-09-24. Scope: the [Logfire Chat Session Audit Trail PRD](../PRD.md), [PR #25 review](https://github.com/AkaiS/california-political-knowledge-map/pull/25), and the installed Logfire 4.37.0 SDK. This note recommends a policy; it does not change runtime behavior.

## Finding

The latest unresolved [review thread](https://github.com/AkaiS/california-political-knowledge-map/pull/25#discussion_r4099354670) reports that `session ID: <credential>` is retained when the credential has no other keyword recognized by Logfire. This follows from the current [_SESSION_CREDENTIAL expression and callback](../../../../src/knowledge_map/utils/telemetry.py): the expression accepts `session_id` but not a space before `ID`; the callback then returns the complete value when Logfire matches `session`. A local read-only check with Logfire 4.37.0 confirmed that `session ID: opaque-123` under `original_question` was returned unchanged with no scrub note. The [preceding resolved thread](https://github.com/AkaiS/california-political-knowledge-map/pull/25#discussion_r4099245091) showed the opposite error: treating every `session ID` as a credential erased a benign legislative question. [Local code](../../../../src/knowledge_map/utils/telemetry.py).

Logfire's default patterns include `session`, `credential`, `password`, `api[._ -]?key`, and other terms. Its callback receives a path, the whole value, and the *first* regex match. Returning the value keeps that entire value; returning `None` redacts it. In the installed SDK, a mapping key match gives the callback the whole mapping value, a string match gives it the whole string, and a JSON string may be decoded and visited recursively. One benign `session` match therefore cannot authorize an entire question, answer, or nested source snapshot. [Logfire scrubbing guide](https://pydantic.dev/docs/logfire/instrument/python/scrubbing/); [Logfire API reference](https://pydantic.dev/docs/logfire/api/logfire/#logfire.ScrubMatch); installed `logfire/_internal/scrubbing.py` lines 38–64, 69–112, 305–347.

The project deliberately captures the original question, rendered answer, and stored passages, with the answer prepared before browser emission. It also promises exact text when the accepted payload fits. Those fields are user or source controlled and may contain credentials. The current [capture tests](../../../../tests/test_chat_session_trail.py) prove two examples (`api_key=` redaction and benign `legislative session ID` retention); they cannot establish safety for arbitrary text. [PRD](../PRD.md#implementation-decisions); [answer ticket](../issues/06-trace-the-prepared-retrieval-answer.md); [tests](../../../../tests/test_chat_session_trail.py).

## The ambiguity

The bytes `session ID: opaque-123` alone do not say whether the value is a public legislative identifier or a private session token. A detector that preserves every such phrase necessarily preserves some credentials. A detector that treats every such phrase as private necessarily loses some benign exact text. Even a larger regex cannot guarantee both properties because a secret can have no recognizable prefix or format. OpenTelemetry states that telemetry tooling cannot determine what is sensitive in an application's context on its own and recommends minimizing sensitive collection. Logfire specifically warns that regex scrubbing of LLM content has both false positives and false negatives and recommends excluding message content when it may be sensitive. [OpenTelemetry sensitive-data guidance](https://opentelemetry.io/docs/security/handling-sensitive-data/); [Logfire scrubbing guide](https://pydantic.dev/docs/logfire/instrument/python/scrubbing/#llm-and-ai-messages).

## Recommendation for this PR

Prefer a **provenance-based exception**: keep the exact-path exemption only for the ID generated by the application, and remove the value-based `session` exemption across question, correction, answer, and source fields. Keep Logfire's default scrubber enabled. No user or retrieved text should become trusted merely because it resembles political language. Validate that the `chat_session_id` attribute is populated solely from the generated Chat Session ID at emission points. The ID remains the reliable search key. This directly closes the reported `session ID:` leak for Logfire-detectable `session` wording without a growing custom credential parser. [Current callback and ID path](../../../../src/knowledge_map/utils/telemetry.py); [Logfire callback contract](https://pydantic.dev/docs/logfire/instrument/python/scrubbing/#scrubbing-less-with-a-callback); [OpenTelemetry sensitive-data guidance](https://opentelemetry.io/docs/security/handling-sensitive-data/).

This requires an explicit product-contract adjustment: describe question and answer text as exact **only when scrubbing leaves it intact**, and use the scrub note to flag redacted fields. A benign question containing `legislative session ID` will be redacted as a false positive under Logfire's default policy. If exact wording for that question is mandatory, the safe route is a separate, trusted structured legislative identifier (when available), not a blanket exception for arbitrary free text. If the PRD's unconditional exact-text promise must remain, it is incompatible with a guarantee that arbitrary credentials in that same free text never reach Logfire. [PRD](../PRD.md); [trail inspection guide](../../../../docs/chat-session-trails.md#retention-and-missing-observations); [OpenTelemetry sensitive-data guidance](https://opentelemetry.io/docs/security/handling-sensitive-data/).

Logfire's built-in matching is a backstop, not proof that all secrets are masked. A bare opaque token with no matching keyword may still pass; the strongest protection is to omit untrusted content from telemetry or put it under a controlled access and retention policy outside this PR's scope. Also review Pydantic AI message capture separately: Logfire documents that its scrubber skips LLM message attributes, and `include_content=False` removes prompts, completions, and tool content if the application decides those may contain secrets. [Logfire scrubbing guide](https://pydantic.dev/docs/logfire/instrument/python/scrubbing/#llm-and-ai-messages); [Pydantic AI content exclusion](https://pydantic.dev/docs/ai/integrations/logfire/#excluding-prompts-and-completions); [current configuration](../../../../src/knowledge_map/utils/telemetry.py).

## Tests to add with an implementation

Use the existing offline ASGI and Logfire-export seam, asserting both captured attributes and unchanged browser output. [PRD testing decisions](../PRD.md#testing-decisions); [existing tests](../../../../tests/test_chat_session_trail.py).

1. Generated `chat_session_id` remains an unscrubbed UUID on start, correction, approval, and answer observations; an arbitrary value supplied in question text never reaches that attribute. [PRD identity decision](../PRD.md#implementation-decisions).
2. `session ID: opaque-123`, `session_id=opaque-123`, and `session-token: opaque-123` in a question or correction yield no raw token in captured audit attributes; inspect the scrub note as well. [Latest PR review](https://github.com/AkaiS/california-political-knowledge-map/pull/25#discussion_r4099354670); [Logfire scrub notes](https://pydantic.dev/docs/logfire/instrument/python/scrubbing/).
3. A single value mixing benign legislative text and a credential (`Which bills were in the 2025-2026 session? session ID: opaque-123`) must not be preserved wholesale. For the recommended policy, the entire scalar may be scrubbed. [Installed SDK whole-value behavior](https://pydantic.dev/docs/logfire/instrument/python/scrubbing/).
4. `rendered_text` and each nested `selected_sources[*].citation`/`passages[*].text` path are exercised with secret-like content, including an earlier benign `session` in the same string and a separate nested passage. Assert no raw credential occurs anywhere in the exported observation. [Answer snapshot contract](../issues/06-trace-the-prepared-retrieval-answer.md); [installed SDK recursive behavior](https://pydantic.dev/docs/logfire/instrument/python/scrubbing/).
5. Record the deliberate false-positive case: `legislative session ID 2025-2026` is scrubbed under the conservative policy, with an appropriate scrub note; adjust the current exact-retention assertion and docs to match the chosen policy. [Current test](../../../../tests/test_chat_session_trail.py); [Logfire default patterns](https://pydantic.dev/docs/logfire/instrument/python/scrubbing/).
6. Demonstrate the known false negative with a bare opaque value in a controlled offline test or document it plainly; do not assert that generic secret detection is complete. [Logfire LLM-content warning](https://pydantic.dev/docs/logfire/instrument/python/scrubbing/#llm-and-ai-messages); [OpenTelemetry sensitive-data guidance](https://opentelemetry.io/docs/security/handling-sensitive-data/).

## Follow-up: exception status text

A focused implementation review on 2026-09-25 found another route outside the
audit-attribute callback. Logfire 4.37.0 treats `exception.message` and
`exception.stacktrace` as safe keys, so its scrubber skips them. An exception
that quotes `session ID: opaque-credential-123` can also put those bytes in the
span status description. The exception callback can suppress exception events,
but native Pydantic AI spans may set the raw status description after that
callback runs. An offline reproduction confirmed this on both manual and model
spans. The [Logfire SQL reference](https://pydantic.dev/docs/logfire/reference/sql/)
exposes that description as `otel_status_message`. Complete protection for
exception text requires filtering the exported status and event data before it
reaches Logfire, for example through an
[OpenTelemetry Collector](https://pydantic.dev/docs/logfire/instrument/python/otel-collector-scrubbing/).
The narrowed audit callback closes the reported attribute leak, but does not
claim that all telemetry from a failed run is free of private text.
